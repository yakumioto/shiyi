# 并行实施

一次开工两张以上的票时读这一篇。它描述的是本仓库已经验证过的工作方式，
不是通用最佳实践。

并行实施只有一个真正的风险：**接口漂移**。四个实施者各写一个包，接缝对不上，
合并时才暴露；此时每个依赖它的包都要返工。下面的顺序就是为了把这件事提前到零成本。

## 1. 先冻结接缝，再派单

在派任何实施者之前，把跨包的契约写成**已提交的代码**：

- 接口（`type X interface`）与共享类型；
- 错误哨兵（`ErrUnavailable` 这类，上层的错误码映射靠 `errors.Is` 穿透）；
- 构造器签名；
- 线格式（HTTP 请求/响应结构体、错误码常量）。

再附一份简短的接缝清单，写清每个包归谁、包之间的依赖方向、错误映射表。

**完成判据**：接缝文件已进集成分支，且 `make check` 绿。

**为什么是承重项**：一个实施者只看到派单那一刻的快照。它写到一半发现契约不合理时，
要么改（下游全崩），要么绕（漂移）。两者都要返工。把它提前到派单之前，成本是零。

## 2. 一票一工作树，一票一分支

```bash
git worktree add .worktrees/<票号> -b tkt/<票号> feat/<集成分支>
```

派单里写明工作树路径与分支名。实施者开工第一件事是确认自己的工作树基于集成分支的
最新 tip，不是就先重置过去。

**完成判据**：实施者报告之前，已把自己的分支 merge 上集成分支 tip 并解决冲突。

## 3. 按前沿派单

票头部的 `Blocked by:` 就是依赖图。只派 `Blocked by` 全部关闭的票。
一次把当前前沿全部派完，让它们真正并行。

**完成判据**：当前没有「未开工且已就绪」的票。

## 4. 一次合并一张，每张跑一次门禁

合并一张，`make check`，再合下一张。

**完成判据**：`make check` 绿，且集成分支上每个包都能编译。

## 5. 工作树只在所有者报告之后才能删

所有者还在跑的时候删掉工作树，等于丢掉它未提交的实现。删之前确认：
它的分支已经合并，或者已经明确决定放弃。

**完成判据**：`git worktree list` 只剩主仓库；所有票分支要么已合并，要么已明确放弃。

## 派单里必须写什么

11 次派单里反复要写的是同样四件事。缺任何一件，实施者都要回来问：

| 项 | 内容 |
| --- | --- |
| 写范围 | 这个实施者**只**能改哪些目录/文件，以及冻结文件不能改 |
| 落点 | 工作树路径、分支名、基于哪个集成分支 |
| 完成判据 | 收工前必须跑的命令（`make check`）与必须全绿的条件 |
| 报告要求 | 做了什么、验收点怎么验的、改动文件清单、对冻结接缝的偏离或增补 |

## 已知会出问题的地方

- **一个实施者跨票写多个包**：写范围重叠，合并时互相覆盖。按包切分，不按票切分。
- **接缝文件在派单之后被修改**：下游实施者看到的是旧快照。要改接缝，先停下所有实施者，
  改完、合并、再重新派单。
- **测试只测各自包的正常路径**：跨包的接缝行为没人测。接缝上要有一个走真实组件的用例。
