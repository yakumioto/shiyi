# 02: 查询路径：从记录中检索并带引用回答

**What to build:** 用户先记录事实，再提出一个问题；Shiyi 能在记录中做字面检索，让 LLM 基于命中记录生成回答，并把每条依据以「记录时间 + 原文」返回。没有命中时明确说没有找到，而不是凭常识回答。查询不写任何文件。

**Blocked by:** 01 (记录路径).

**Status:** ready-for-agent

- [x] 先记录两条事实，再提交查询，返回 200、`kind:"query"`、`status:"ok"`，回答内容来自记录。
- [x] 每个引用都包含 `time` 和 `content`，且 `time` 与已写入记录一致。
- [x] 没有命中时返回 `status:"no_match"`，回答为固定的「没有找到相关记忆」，引用为空。
- [x] 查询前后数据文件内容完全不变。
- [x] 模型引用本次检索未返回的记录时，返回 502 `invalid_citation`，不返回回答。
- [x] 本切片只支持一次检索调用；多轮检索在 03 补齐。
- [x] 测试使用假 LLM 覆盖命中、无命中、非法引用，可在无网络环境运行。

## Comments

已完成。集成在 `feat/shiyi-v1`。

- 检索：`internal/search`（`rg -l -F -i` 预筛 + Go 侧只匹配 `content`、time 降序、去重、limit）。
- 回答：`internal/answer`（`search_memory` 单/多轮、引用校验、`no_match` 固定回答且丢弃模型文本）。
- 引用以 `{time, content}` 返回，客户端无需二次请求。
- 验证：检索缝用真实 `rg` + 临时目录；回答缝用假模型；覆盖命中、无命中、非法引用、查询不落盘。

### 后续加固

- **检索的行上限与存储对齐**：原先检索按 1 MiB 原始输入估算单行上限，而 JSON 编码后的
  行可能翻倍，于是一条被正确保存的记录在查询时读不出来（500 `search_failed`）。现在
  检索与存储共用 `store.MaxLineBytes`，并有 1 MiB 转义字符原文的回归用例。
